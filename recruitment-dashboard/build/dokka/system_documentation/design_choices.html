Design Choices

General Flow and Design of the Route

The overall flow of the recruitment dashboard system involves several key steps:

  1. New Jira tickets in the JSON file returned by the API endpoint are processed.
  2. Recruitment stats are calculated by the RecruitmentStatsService.
  3. Duplicates between Jira and LinkedIn applications are removed by the DuplicateApplicantDeletionService.

Handling Duplicate Applicants

To prevent counting the same applicant multiple times (e.g., from both Jira and LinkedIn applications), the system checks for duplicates and removes entries from the LinkedInApplicants table if a corresponding Jira issue is found. For this purpose we save the names of applicants through LinkedIn in the linked_in_applicant table and the names of applicants through Jira in the applicant_names table and match these against each other in the DuplicateApplicantDeletionService.

Single Database Table for Jira Issues

Initially, Jira issues for applicants, interns, and vacancies were stored in a single table. This approach simplifies the database schema but requires additional logic to distinguish between different issue types. Eventually, the design was adjusted to use a discriminator column and subclasses for different issue types to better separate the data and streamline processing.

JiraIssue Entity

The JiraIssue class is an abstract base class representing a Jira issue in the database. It serves as the parent class for different types of issues, such as intern, applicant, and vacancy issues. The inheritance strategy is set to single-table inheritance (SINGLE_TABLE), meaning all subtypes are stored in a single database table. The DiscriminatorColumn is used to distinguish between different issue types. A custom deserializer JiraIssueDeserializer is used to convert JSON data into specific subtypes based on the discriminator column.

Subtypes of JiraIssue

The JiraIssue entity has several subtypes, including InternIssue, ApplicantIssue, VacancyIssue, and InternVacancyIssue. Using the discriminator column allows for querying different types of Jira issues easily.

Calculating Recruitment Stats

The RecruitmentStatsService class is responsible for updating and managing recruitment statistics. This service handles the calculation and logging of various recruitment metrics such as the average time to hire, the current number of active applicants, and the logging of hiring events. Here's an overview of the process:

  • Average Time to Hire: The system calculates the average number of days it takes for issues to transition to a hiring status. This involves retrieving relevant status changes, calculating the duration between issue creation and status change, and averaging these durations.
  • Current Active Applicants: The system counts the number of Jira issues that are currently in an active status. This is done by querying the database for issues in specific ongoing statuses.
  • Applicants by Stage: The system logs the number of applicants at each stage of the recruitment process. This information is saved in the ApplicantsStageLog table.
  • Average Time to Fill Vacancies: Similar to the average time to hire, this metric calculates the average duration for issues to reach a status indicating a filled vacancy.

Custom Deserializer for Jira Issues

To handle the complexity of parsing Jira issue data, a custom deserializer is implemented. The JiraIssueDeserializer class is responsible for parsing JSON data into various JiraIssue subtypes, such as InternIssue, ApplicantIssue, InternVacancyIssue, and VacancyIssue, based on the issue type in the JSON input. The deserializer extracts and converts JSON fields into respective entity attributes, including nested structures like the changelog history. It ensures that status changes are accurately captured and associated with their respective JiraIssue instances.

IssueStatus Enum

The IssueStatus enum represents the status of an issue within the recruitment process. It classifies various stages of the recruitment process by defining specific statuses. Each status is associated with flags indicating whether it represents an open vacancy, an active applicant's process stage, or a successful hire.

Vacancy Statuses:

  • VAC_OPEN - Indicates an open vacancy. (vacFilled = false, activeApplicant = false, successfulHire = false)
  • KDD_IN_PROCEDURE - Indicates that a vacancy is in the procedure. (vacFilled = false, activeApplicant = true, successfulHire = false)
  • GEEN_KDD_IN_PROCEDURE - Indicates that no vacancy is in the procedure. (vacFilled = false, activeApplicant = true, successfulHire = false)
  • CLOSED___NIET_VERVULD - Indicates that a vacancy is closed and not filled. (vacFilled = false, activeApplicant = false, successfulHire = false)
  • CLOSED___VERVULD - Indicates that a vacancy is closed and filled successfully. (vacFilled = true, activeApplicant = false, successfulHire = true)

Applicant/Intern Statuses:

  • OPEN - Indicates an open applicant process. (vacFilled = false, activeApplicant = true, successfulHire = false)
  • BEOORDELING - Indicates that an applicant is under review. (vacFilled = false, activeApplicant = true, successfulHire = false)
  • EERSTE_GESPREK - Indicates that an applicant is in the first interview stage. (vacFilled = false, activeApplicant = true, successfulHire = false)
  • TWEEDE_GESPREK - Indicates that an applicant is in the second interview stage. (vacFilled = false, activeApplicant = true, successfulHire = false)
  • DERDE_GESPREK - Indicates that an applicant is in the third interview stage. (vacFilled = false, activeApplicant = true, successfulHire = false)
  • CLOSED___NIET_OP_GESPREK - Indicates that an applicant process is closed and no interview occurred. (vacFilled = false, activeApplicant = false, successfulHire = false)
  • CLOSED___NA_1E_GESPREK - Indicates that an applicant process is closed after the first interview. (vacFilled = false, activeApplicant = false, successfulHire = false)
  • CLOSED___NA_2E_GESPREK - Indicates that an applicant process is closed after the second interview. (vacFilled = false, activeApplicant = false, successfulHire = false)
  • CLOSED___NA_3E_GESPREK - Indicates that an applicant process is closed after the third interview. (vacFilled = false, activeApplicant = false, successfulHire = false)
  • CLOSED___HIRED - Indicates that an applicant has been successfully hired. (vacFilled = false, activeApplicant = false, successfulHire = true)

Interaction with the Database

Interaction with the database is handled via repository interfaces. The most important one is the JiraIssueRepository, which provides methods for retrieving issue data, including average time to a specific status, count of issues by status, and generation of hiring event records based on status changes. Key methods include:

  • findStatusChangesForCalculation: Retrieves all status changes for a given status for ApplicantIssue and VacancyIssue types, filtering out intern-related issues.
  • averageTimeToStatus: Calculates the average time it takes for issues to reach a specified status.
  • countByCurrentStatus: Counts the number of Jira issues currently in a specified status.
  • findByCurrentStatus: Finds all Jira issues currently in a specified status.
  • countByCurrentStatusIn: Counts the number of Jira issues for each status in a given collection of statuses.
  • findHiringEvents: Finds hiring events for applicants based on status changes indicating a hire.
  • findInternHiringEvents: Finds hiring events for interns based on status changes indicating a hire.
  • findAllApplicantIssues: Finds all ApplicantIssue objects.
  • findAllInternIssues: Finds all InternIssue objects.
